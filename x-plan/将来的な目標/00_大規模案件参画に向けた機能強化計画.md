# 大規模案件参画に向けた機能強化計画

## 目的

このプロジェクトを、ClearMLの画面や単発学習を試す段階から、チームで継続運用するMLOps案件の主要工程を一通り説明・実装できる学習環境へ引き上げる。

対象は機械学習コードだけではなく、データ、実験管理、実行基盤、モデル提供、監視、Angular Web、CI/CD、セキュリティ、運用を含む。

## 現状の到達点

2026-09-07時点で、次は実装・確認済みである。

- Docker ComposeによるローカルClearML Server
- 半導体データの生成、ClearML Dataset 2バージョンの登録、冪等なseed
- Dataset Versionを明示したRandomForestの学習
- train / validation / test分離、入力検証、前処理、評価
- Parameters、Metrics、confusion matrix、Artifact、Output ModelのClearML記録
- Angular 22版ClearML WebとClearML APIの接続
- Python単体テスト208件成功（`ml` 199件、`tools` 9件）
- Angular単体テスト111件成功、本番ビルド成功
- Playwright E2E 2シナリオとE2E TypeScriptチェック

現状は「再現可能な単発実験」の段階であり、「共有実行基盤上で自動的に学習し、審査したモデルを配備し、監視して改善する」工程がまだつながっていない。

## 優先順位の基準

優先順位は、次の順で判断する。

1. 後続機能の土台になるか
2. 大規模案件で障害・誤配備・情報漏えいを防ぐか
3. ClearMLを使う実務フローを端から端まで学べるか
4. 複数人・複数環境でも再現できるか

## 計画の進め方

全項目を同じ深さで完成させてから次へ進むのではなく、最初に小さなend-to-endの縦スライスを完成させる。

```text
Dataset
  -> Queue / Agent
  -> Pipeline
  -> Train / Evaluate
  -> Model Gate / Registry
  -> Deploy / Predict
  -> Angularから起動・状態確認
```

第一ゴールでは、各要素を本番相当まで作り込まない。正常系と代表的な失敗系が動き、境界・責務・データの流れを説明できる最小構成にする。その後、Data Quality、Observability、Security、Testing、CI/CD等を横断的に厚くする。

この順序により、「巨大な基盤の一部だけが未完成で残る」状態を避け、「小さいがDatasetから推論まで接続されたシステム」を先に完成させる。

第一のPipelineとEvaluation Gateを構築するまでは、機械学習アルゴリズムをRandomForestに固定する。モデル精度の追求ではなく、次のtraceabilityを学習の中心に置く。

- 誰が実行したか
- どのDataset Version、コード、実行環境、パラメータを使ったか
- どの評価結果によってモデルを採用したか
- どこへ配備し、現在どのモデルが利用されているか

PipelineとEvaluation Gateが最低限動いた後は、Servingへ進む前に期間を区切ったモデル比較スパイクを挟んでもよい。これは機械学習を封印するための固定ではなく、基盤構築中に論点を増やさないための固定である。参画準備の期限を圧迫する場合はスパイクを省略し、Servingへ進む。

## P0: 第一ゴールとなる縦スライス

### 1. 最低限のCIと再現可能な実行入口

**不足**

- CI設定がなく、build・test・lint・E2Eが変更ごとに自動実行されない
- Python依存は範囲指定だけでlockされておらず、Python本体のバージョンも固定されていない
- `web:lint` は2,927件（error 2,871、warning 56）で失敗する
- Angularの本番ビルドは成功するが、direct `eval` の警告とテスト時のAngular runtime警告が残る

**実装するもの**

- GitHub Actions等でPython test、Angular test、E2E typecheck、production buildを自動実行
- Queue / Pipeline / Servingで使うPythonバージョンと最小限の依存を固定
- ローカルとCIで同じ検証コマンドを使う
- Angular lint 2,927件の全件解消は第一ゴールの前提にしない
- 新規・変更範囲で既存違反を増やさない暫定ルールを置く

**完了条件**

- 新規cloneから共通コマンドで検証できる
- 縦スライスの主要コードを壊した変更がCIで失敗する
- CIの高度化や既存lint負債の解消が、Queue / Agent以降の着手を妨げない

### 2. ClearML Queue / Agentによるリモート実行

**不足**

- 学習は開発者端末のローカルCLI実行のみ
- Queue、Agent、実行用コンテナ、CPU/GPU等のリソース分離がない
- ClearML TaskにGitリポジトリURLを取得できない警告があり、コード来歴が不完全

**実装するもの**

- 学習用Dockerfileをmulti-stageで作成し、非root・healthcheck・固定依存を採用
- `clearml-agent` と学習QueueをComposeへ追加
- ローカル実行とQueue投入を同じTrainingConfigで扱うlauncherを追加
- Git SHA、image digest、Dataset ID、実行者、Queue名をTaskへ記録
- 正常完了と代表的な失敗Taskの確認手順を用意

**完了条件**

- CLIからQueueへTaskを投入し、Agentが取得して学習を完了できる
- 開発端末に学習依存がなくても、同じ入力から同等の結果を再現できる
- 成功・失敗の状態をWebとテストで確認できる

### 3. ClearML Pipelineによる学習ワークフロー自動化

**不足**

- Dataset検証、学習、評価、モデル登録が1プロセスに直列結合されている
- ステップ再利用、キャッシュ、途中再実行、依存関係の可視化がない

**実装するもの**

- `validate dataset -> preprocess -> train -> evaluate -> register candidate` を独立Task化
- ClearML Pipelineで入出力ArtifactとDataset Versionを明示して接続
- Dataset検証失敗時に後続ステップへ進まないことを確認
- cache、retry、timeout、通知は縦スライス完成後の強化項目とする

**完了条件**

- Pipeline画面で各ステップ、依存関係、入出力、所要時間を追跡できる
- 正常系と検証失敗系を実行し、どのステップで停止したか確認できる

### 4. モデル評価ゲートとRegistry上の昇格フロー

**不足**

- Output Modelは保存されるが、candidate / staging / productionの状態管理がない
- 採用基準、既存productionモデルとの比較、承認・却下の監査証跡がない

**実装するもの**

- 第一段階はrecallとF1の最小限の合格基準を設定ファイル化
- 基準未達時にcandidate登録へ進めない評価ゲート
- model tagsまたはmetadataを使ったcandidate / staging / production昇格
- 第一段階の昇格操作は手動承認でもよいが、承認者、理由、元Task、Dataset ID、評価結果を記録
- rollback対象を一意に特定できるモデル命名・バージョン規約

**完了条件**

- 基準未達モデルはproductionへ進めない
- productionモデルから学習Task・コード・Dataset・承認履歴へ追跡できる
- 直前のproductionモデルへ戻す手順を実演できる

### 寄り道: 期間限定のモデル比較スパイク

**位置付け**

PipelineとEvaluation GateをRandomForestで一度完成させた後、学習アルゴリズムへの理解を広げる任意課題として実施する。HPO、特徴量開発、網羅的なアルゴリズム調査とは分離し、1〜2回の学習セッションなど終了条件を先に決める。

**比較するモデル**

- `LogisticRegression`: 単純で説明しやすい線形分類の基準線
- `RandomForestClassifier`: 現在の基準モデル
- `HistGradientBoostingClassifier`: RandomForestと学習特性が異なるBoosting系の代表

scikit-learn内の3系統に限定し、XGBoost、LightGBM、CatBoost、SVM、ニューラルネットワーク等へはこの段階で広げない。

**比較条件**

- Dataset Version、train / validation / test分割、random seed、前処理、評価契約を揃える
- HPOやモデルごとの特徴量追加を行わず、原則としてモデル部分だけを差し替える
- validationのprecision、recall、F1、学習時間、推論時間、モデルサイズをClearMLへ記録する
- モデルの比較・選定にはvalidationを使い、testは選定後のモデルに対する最終確認で一度だけ使う
- 「最高精度」だけでなく、速度、サイズ、説明可能性を含む採用理由を残す

**このスパイクで確認する設計**

- trainerの共通contractからモデル固有実装を分離できているか
- PipelineやEvaluation GateがRandomForest専用になっていないか
- 同じ条件の実験をClearML上で比較・追跡できるか
- 採用モデルからDataset、Task、コード、評価結果へ遡れるか

**完了条件**

- 3モデルの比較結果と採用理由をClearMLおよび学習資料で説明できる
- モデル差し替えがPipeline、評価、Registryの大幅な変更を必要としない
- スパイク終了後はServingの実装へ戻り、精度改善を際限なく続けない

### 5. 最小の推論サービスとデプロイ

**不足**

- 登録モデルを実際に利用する推論経路がない
- 入力・出力契約、互換性、段階リリース、rollbackがない

**実装するもの**

- FastAPI等による最小のonline推論API
- Pydantic等によるschema、モデルmetadata、health / readiness endpoint
- Registryのproductionモデルを取得し、起動時に整合性を検証するadapter
- Docker化、smoke test、直前モデルへのrollback手順
- timeout等の代表的な異常系のcontract test

**完了条件**

- productionへ昇格したモデルだけが推論環境へ配備される
- 不正入力を4xxで拒否し、model versionを応答・ログから確認できる
- 新旧モデルの切替とrollbackを確認できる

### 6. Angularから一連の流れを操作・追跡

**不足**

- Angular Webは存在するが、今回作るPipeline起動から結果確認までの配線を学習対象として整理できていない
- ボタン操作、API Client、state、Effects、ClearML API、Task状態の対応を端から端まで説明できる資料・テストがない

**実装するもの**

- 第一段階では既存画面を読み、Task一覧・詳細について`Component -> state -> Effects -> API Client -> ClearML API`をtraceする
- 次に、最小のPipeline起動操作と実行状態・評価結果・model versionの確認経路をAngularへ追加する
- 更新対象stateのfeature配下にEffectsを置き、API modelと画面用modelの変換境界を明示する
- loading、成功、失敗、キャンセル、再読込時のstate遷移をテストする
- `Angular -> ClearML API -> Task -> Pipeline -> Queue -> Agent -> Training -> Artifact / Model`のシーケンス資料を作る

**完了条件**

- 画面操作からTask生成、Agent実行、Model登録までをコード上で追跡し、自分の言葉で説明できる
- AngularからPipelineを起動し、実行状態と最終モデルを確認できる
- API失敗や古いTaskの応答によって誤った状態を表示しない

## P1: 縦スライスを横断的に強化

### 7. データ品質・lineage・drift検知

**不足**

- 現在のCSV検証は必須列、型、有限値、ラベル、重複ID等が中心
- 分布変化、外れ値、欠損率、カテゴリ増加、学習時と推論時のskewを検出しない

**実装するもの**

- データ契約をコードと機械可読schemaで一元管理
- 列ごとの範囲、欠損率、unique率、カテゴリ集合、クラス比率の検証
- Dataset Version間の統計比較とdata driftレポート
- raw -> curated -> training Datasetのlineageとproducer情報
- 検証失敗時の隔離、再処理、承認例外フロー

**完了条件**

- 意図的に壊したDatasetを学習前に停止できる
- どの原本・変換処理から学習Datasetが作られたか追跡できる
- drift閾値超過をArtifactと通知で確認できる

### 8. 観測性と運用アラート

**不足**

- ローカルログとClearML画面の手動確認が中心
- サービス、Pipeline、Agent、インフラのSLO・メトリクス・通知がない

**実装するもの**

- 構造化ログ、correlation ID、Task ID、model versionの共通付与
- Prometheus / OpenTelemetry等による成功率、latency、throughput、Queue滞留、資源使用量
- prediction drift、性能劣化、エラー率のダッシュボードとアラート
- SLI / SLO、alert severity、runbook、postmortemテンプレート

**完了条件**

- 失敗を注入し、メトリクスから検知してrunbookで原因Taskまで到達できる
- 誤検知を抑えたwarning / critical通知を確認できる

### 9. 認証・認可・secret・サプライチェーン対策

**不足**

- ローカルComposeではElasticsearchのsecurityが無効で、各ポートをhostへ公開している
- RBAC、secret manager、TLS、依存脆弱性・コンテナスキャンがない

**実装するもの**

- 開発・検証・本番の脅威モデルとデータ分類
- 最小権限RBAC、サービスアカウント、credential rotation
- secretを環境変数サンプルやTask Parametersへ混入させない仕組み
- TLS、network policy、監査ログ、保存時暗号化
- dependency / secret / SAST / container / SBOM scanをCIへ追加

**完了条件**

- 権限別の許可・拒否を統合テストで確認できる
- リポジトリ、build成果物、Taskログにsecretが含まれない
- critical vulnerabilityをリリースゲートで拒否できる

## P2: 中優先

### 10. Angularの品質負債解消とアーキテクチャ境界の強化

**不足**

- TypeScriptの`strict`がfalse
- lint違反が大量にあり、`any`、未使用、accessibility、旧DI記法等が混在
- Effectsの配置やfeature境界が一貫せず、変更影響を制御しにくい
- production buildのinitial bundleが約3.09 MBで、全体budgetが設定されていない

**実装するもの**

- feature単位で`strict`移行し、新規コードでは例外を許可しない
- API generated modelとdomain / view modelをadapterで分離
- state更新対象feature配下へEffectsを配置し、facade / selector境界を整理
- standalone、Signals / NgRxの責務、lazy route、error handling方針をADR化
- accessibility、runtime warning、bundle budgetを継続的に改善

**完了条件**

- 変更対象featureがstrict・lint・単体テストを通る
- feature間の禁止依存を静的チェックできる
- initial / lazy chunkのbudget超過でCIが失敗する

### 11. CI強化と統合・契約・E2E・非機能テストの拡充

**不足**

- Playwrightは2シナリオだけで、主な画面フローを覆わない
- APIモック中心で、実ClearML Serverとのend-to-end経路を検証しない
- 性能、耐障害性、ブラウザ互換性、accessibilityの自動検証がない
- Pythonのformatter、linter、型チェック、カバレッジ閾値がない

**実装するもの**

- Dataset登録 -> Queue学習 -> 比較 -> 昇格 -> 推論のsmoke E2E
- OpenAPI / JSON Schema等によるconsumer-provider contract test
- unit、component、integration、E2Eの責務を定めたtest pyramid
- retry、timeout、API停止、破損Artifact等のfailure test
- k6等の負荷試験、axe等のaccessibility試験、主要ブラウザmatrix
- flaky testの隔離ではなく検知・原因修正・再発防止の運用
- Ruff、mypyまたはPyright、coverageと依存lockを導入
- Angular lintはbaselineを段階的に縮小し、build budgetと警告許容方針をCIへ追加

**完了条件**

- staging相当環境で主要業務フローを自動検証できる
- API破壊変更、性能劣化、重大なaccessibility違反をリリース前に検知できる
- 新規・変更コードにlint、型、テスト、カバレッジの品質ゲートが適用される

### 12. 実験設定管理とHyperparameter Optimization

**位置付け**

HPOはMLOpsの縦スライス完成後に扱う。PipelineとEvaluation Gateの後に行う期間限定の3モデル比較とは別の課題であり、第一ゴールでは精度向上より実行来歴・評価・昇格・配備のtraceabilityを優先する。

**不足**

- RandomForestの少数引数だけを手動変更して比較している
- 構造化設定、探索、最良モデル選定がない

**実装するもの**

- dev / staging / production設定とsecretを分離した構造化設定
- ClearML Optimizationによる探索、早期停止、並列数・計算予算の上限
- cross validation、class imbalance対応、確率閾値調整
- 探索結果から評価ゲートへcandidateを渡す処理
- 新しいアルゴリズムの追加は、期間限定スパイクで不足が明確になった場合だけ検討する

**完了条件**

- 探索空間、目的指標、予算がTask上で再現可能
- testデータをモデル選定に使わず、最終評価を一度だけ行う

## P3: Enterprise運用への拡張

### 13. 実環境を想定したInfrastructure as Codeと災害復旧

**不足**

- 単一ホストのDocker Composeとnamed volumeだけで、環境差分、冗長化、backup / restoreがない

**実装するもの**

- Terraform等でnetwork、compute、object storage、database、secret、monitoringをコード化
- Kubernetesまたはマネージドサービス上のdev / staging / production分離
- immutable image、artifact promotion、GitOps等による環境反映
- MongoDB、Elasticsearch、file storageのbackup / restore演習
- RPO / RTO、容量計画、コストタグ、resource quota

**完了条件**

- staging環境をIaCから再作成でき、手作業の設定差分がない
- backupから別環境へ復旧し、Dataset・Task・Modelの整合性を確認できる

### 14. チーム開発標準とドキュメント

**不足**

- READMEはローカル学習には詳しいが、設計判断、責任分界、リリース、障害対応の資料が不足

**実装するもの**

- C4図、データフロー、ML lifecycle、環境構成図
- ADR、coding standard、Definition of Done、review checklist
- CODEOWNERS相当のownership、branch / release / versioning規約
- onboarding、運用runbook、障害訓練、postmortem
- model card、dataset card、評価上の制約・公平性・利用禁止条件

**完了条件**

- 新規参画者が資料だけで環境構築し、変更箇所と担当境界を判断できる
- 障害・rollback・モデル再学習をrunbookに沿って実施できる

### 15. コスト・容量・ライフサイクル管理

**不足**

- 実験、Artifact、Dataset、ログの保持期限と費用上限がない

**実装するもの**

- project / team / Task単位のcost attribution
- Queue優先度、並列数、CPU/GPU quota、停止ルール
- Dataset / Model / Artifact / logのretentionとarchive / delete policy
- HPOのbudget上限、idle Agent停止、容量アラート

**完了条件**

- 実験1回と環境単位の概算費用を可視化できる
- 保存上限や計算予算を超える前に停止・通知できる

## 推奨する実施順

```text
Phase 1: 現在地
  再現可能な単発学習

Phase 2: 共有実行
  最低限CI -> Queue / Agent・学習コンテナ

Phase 3: 自動化
  ClearML Pipeline

Phase 4: モデルライフサイクル
  Evaluation Gate -> Model Registry昇格

Optional Study: 期間限定のモデル比較
  LogisticRegression / RandomForest / HistGradientBoosting
  ※ HPOと特徴量開発は行わず、期限優先時は省略

Phase 5: 利用
  Serving -> Deploy -> Predict -> Rollback

Phase 6: アプリケーションから操作・確認
  Angular -> ClearML API -> Task / Pipeline状態 -> Artifact / Model

Phase 7: 横断品質を強化
  Data Quality / Observability / Security / Testing / CI強化 / Angular品質 / HPO

Phase 8: Enterprise運用へ拡張
  IaC / DR / Cost / 開発標準
```

最初の到達目標は項目1〜6である。ただし各項目の高度化を待たず、次の一連を最小構成で早く通す。モデル比較スパイクを実施する場合も、縦スライス完成を妨げない期間に限定する。

```text
Dataset Version指定
  -> QueueへPipeline投入
  -> データ検証
  -> 学習・評価
  -> 基準を満たすモデルだけcandidate登録
  -> 承認してproduction昇格
  -> 推論環境へ配備・smoke test
  -> Angularから起動・状態・結果を確認
  -> 問題時rollback
```

## 着手時の分割方針

各項目をそのまま巨大なPRにせず、次の単位へ分割する。
